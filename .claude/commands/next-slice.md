description: Run one development slice from docs/backlog.md (orchestrate → sonnet implementer → review → report)
argument-hint: "[slice id, e.g. S1; default = first todo]"
---
You are the orchestrator for one slice: $ARGUMENTS (if empty, the first `todo` row in `docs/backlog.md`). You do not write production code yourself; the `slice-implementer` subagent (sonnet) does. Spend tokens on the spec and on verification, not on typing code.

0. Branch (git flow, see CLAUDE.md): the tree must be clean, except when you are already on `feature/<ID>-*` for this slice — then it is an interrupted run: keep the uncommitted work, check `git status --short`, `git diff --stat` and `uv run pytest 2>&1 | tail -n 15`, and continue from the first unfinished step (re-brief the implementer with what is already there; do not start over). If `feature/<ID>-<slug>` exists, switch to it (resume); otherwise `git switch dev && git switch -c feature/<ID>-<slug>` (slug = 2–3 words, kebab-case, e.g. `feature/S2-excel-loader`). Never work on `dev` or `master` directly.
1. Read the slice's backlog row, `docs/decisions.md`, and the slice's part of `docs/plan.md` (grep the slice ID and decision numbers; do not read the whole plan). For organizer data facts use `docs/data_notes.md`. Mark the slice `doing`.
2. Write the brief to `runs/briefs/<ID>.md` (at most 40 lines): goal, files to create/change, function signatures and data shapes, acceptance tests with concrete numbers, things out of scope. For UI slices add "UI criteria" (numbered) and "Load skill `metro-ui`". Spawn `slice-implementer` with a 3-line prompt: "Slice <ID>. Brief: runs/briefs/<ID>.md. Report ≤10 lines." (the brief lives in the file, not in prompts). Pass `model: haiku` only for slices that touch docs/fixtures without logic.
3. When it reports back, check `git status --short` and `git diff --stat`, then read only the critical parts (formulas, invariants, contract fields), not every file. Run `uv run pytest 2>&1 | tail -n 15` yourself.
4. Spawn `ecc:python-reviewer` on the slice: "Review the uncommitted changes (git diff + untracked files under src/ and tests/). Report only real defects — correctness, invariants, leaks of future data — at most 10 lines, no praise, no style nits ruff already covers."
4a. UI slices (the row touches `app.py`, `assets/`, `figures.py` or says UI): spawn `ui-checker` with "Slice <ID>, brief runs/briefs/<ID>.md". It writes/uses `runs/briefs/<ID>.steps.json`, runs `scripts/ui_check.py`, answers ≤10 lines PASS/FAIL against the brief and `docs/design.md`. Look at no more than one screenshot yourself. FAIL lines are findings for step 5.
5. Send real findings back to the same implementer with SendMessage (its context is warm), not to a new agent. Note the findings you reject and why.
6. Re-run `uv run pytest 2>&1 | tail -n 5` and `uv run ruff check .`. Mark the slice `done`; add new decisions to `docs/decisions.md` in one line each.
6a. Keep the plan current. If the slice changed something later slices rely on (a new data fact, an interface change, a wrong estimate, a slice that is too big, a missing pre-step), update the affected `docs/plan.md` section and `docs/backlog.md` rows (clarify acceptance, split, reorder, add; never rewrite `done` rows) and add a line to `docs/decisions.md`. Do small corrections yourself; for scope changes (dropping a slice, deviating from the ТЗ, breaking a contract the team copies) ask the user first. In a headless run (`claude -p`, i.e. `scripts/slice_loop.sh`) you cannot ask: leave the slice uncommitted, put the question in your report on its own line starting with `NEEDS_USER:`, and stop — the loop halts and notifies the user.
Context budget: never paste long output into your context (`| tail -n 30`), read files with offset/limit, subagent replies ≤10 lines, at most 2 screenshots per slice in total.
7. Report to the user in at most 10 lines: what works, the real test summary, open assumptions, plan changes (or "none"), the proposed commit message. After the OK (the user's in an interactive run, or the loop's automatic OK after its own pytest + ruff gate): commit on the feature branch, then `git switch dev && git merge --no-ff feature/<ID>-<slug> -m "merge: <ID> <slice title>"`, run `uv run pytest 2>&1 | tail -n 3` on `dev`, and `git branch -d feature/<ID>-<slug>`. Never merge to `master` unless asked. Then push: in an interactive run `git push origin dev` yourself (on failure report it, the commits stay local); in a loop run do not push, the loop pushes `dev`. Never push `master` unless asked. Then suggest `/clear` before the next slice — all state lives in the docs files.
